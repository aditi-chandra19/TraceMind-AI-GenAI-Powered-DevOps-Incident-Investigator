# Day 2 setup: accounts, sessions, storage, and log investigation

## Run with local MongoDB in Docker

The normal local setup uses a real MongoDB database. Demo mode is optional and must be explicitly enabled.

1. Install and start Docker Desktop for Windows. Docker Desktop needs the WSL 2 backend; if it prompts you, enable WSL 2 and restart Windows, then wait until Docker Desktop says it is running.
2. In the repository root, create a private environment file and set the database and admin passwords:

   ```powershell
   Copy-Item .env.example .env
   notepad .env
   ```

   Replace `MONGO_ROOT_PASSWORD` with a long random value, use the same value in the password portion of `MONGODB_URI`, and set a unique `JWT_SECRET` (at least 32 characters) and `ADMIN_PASSWORD` (12–72 bytes). `.env` is ignored by Git.

3. Start MongoDB, create the initial administrator and sample incidents, then start the application:

   ```powershell
   npm run db:up
   npm run db:seed
   npm run dev
   ```

4. Open `http://localhost:5173` and sign in with the `ADMIN_EMAIL` and `ADMIN_PASSWORD` values from `.env`. Check `http://localhost:4000/api/health`; its `mode` should be `mongodb`.

MongoDB is published only on `127.0.0.1:27018` (container port 27017), requires the local root credentials, and stores its data in the named `tracemind-mongo-data` Docker volume. The separate host port avoids conflicts with a MongoDB service already installed on Windows. `npm run db:down` stops MongoDB while keeping the data. To delete the database permanently, use `docker compose down -v`.

If `DEMO_MODE=false`, the API now exits with an error when MongoDB is missing or unreachable instead of silently switching to in-memory demo storage.

## Run the application in demo mode

Set `DEMO_MODE=true` in `.env` and leave MongoDB unavailable to use the in-memory sample account and data. This mode is for trying the interface; changes are lost when the API restarts.

From the repository root:

```powershell
npm install
npm run dev
```

Open `http://localhost:5173` and sign in with the demo-only account:

- Email: `admin@tracemind.local`
- Password: `TraceMindDemo!2026`

The demo account is enabled only outside production. In production, set `DEMO_MODE=false`, provide a unique strong `JWT_SECRET` (at least 32 characters), and connect MongoDB. Session JWTs are delivered in `HttpOnly`, `SameSite=Lax` cookies; browser JavaScript does not persist the token. Sessions expire after eight hours and are revoked server-side on sign out.

## Connect MongoDB Atlas

1. Create an Atlas project and development cluster.
2. Create a database user and allow-list the machine IP that runs the API.
3. In **Connect → Drivers → Node.js**, copy the URI and replace its password placeholder. URL-encode special characters in the password.
4. Copy `.env.example` to `.env` and set `MONGODB_URI`. Keep `.env` untracked. The API refuses to claim production storage if the database connection failed.
5. Restart `npm run dev`. `/api/health` reports `mode: mongodb` only after a successful connection. Demo incidents are inserted idempotently. New users, incidents, uploaded log sources, parsed lines, and audit records use MongoDB.

MongoDB Atlas user credentials are not the same as the Atlas login. Restrict network access to the API host; do not use `0.0.0.0/0` for production.

## Add a production administrator

Create a one-off `.env` containing `MONGODB_URI`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD`, then run:

```powershell
npm --workspace apps/api run seed:demo
```

The script inserts the sample incidents idempotently and creates an administrator only if that email is unused. It will not overwrite an existing password. Remove `ADMIN_PASSWORD` from the environment after seeding. New self-registered accounts receive the `analyst` role; only an administrator can create users with the `admin`, `analyst`, or `viewer` role.

## Upload and investigate logs

Sign in as the administrator or an analyst, select **Analyze logs**, and choose one `.log`, `.txt`, `.json`, `.jsonl`, or `.ndjson` file. Uploads are streamed, limited by `MAX_UPLOAD_MB` (default 25 MB), one file per request, 64 KiB per line, and 100,000 lines. Parsed log records retain their source line number. Supported structured fields include common timestamp, severity, service, and Kubernetes event keys.

After upload, TraceMind opens a report with severity, repeated error groups, stack-trace indicators, a basic error-volume anomaly check, diagnostic recommendations, and citations to actual parsed source lines. The report analyzes at most the first 500 stored lines from a source. Reports are generated when requested and are not yet saved as separate investigation records.

Without `OPENAI_API_KEY`, the report is generated by local rules and labeled **Local rules**. To enable model-assisted reports, add an OpenAI API key to the untracked `.env`; `OPENAI_MODEL` selects the model. The server sends at most 120 relevant parsed lines, after redacting credentials, email addresses, IP addresses, phone numbers, and common card/SSN formats. Never upload logs you are not authorized to send to your configured model provider.

Model output is schema-validated and its cited line numbers are checked against the uploaded source before the report displays them. If the provider is unavailable, the report falls back to local rules and says so. If no valid model citations are returned, confidence is capped and the report flags the hypothesis as unverified. Recommendations are advisory; the app never executes remediation.

Demo-mode logs and audit events are in memory and are cleared when the API process restarts; MongoDB mode persists the uploads and parsed lines. Audit events are available at `GET /api/audit` to administrators only.

Never put real credentials in this file or Git. API secrets stay in local `.env`; GitHub Actions secrets will be configured separately when the deployment workflow is added.
